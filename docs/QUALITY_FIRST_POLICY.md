# QUALITY_FIRST_POLICY — 범용 교본 제작·검증 최상위 정책

> **2026-11-11 사용자 논의로 확정된 운영 원칙.** 범위: ROTATION TEXTBOOK / Chat-first 교본 제작 방법론. 개인 HTML·외부 공략 원문은 공개 GitHub에 보관하지 않는다. 과거 독립 AI 자동화 제품 개발을 재개하라는 지침이 아니다.
>
> **우선순위:** 개별 전문화 보완이나 기능 개발 < 다른 전문화에도 전이되는 제작 지식·평가 방법 < 실제 독자의 게임 판단·이해에 대한 검증 가능한 기여.

## 1. 최종 목표와 역할 — 확정 정책

1. 사용자는 ChatGPT에서 전문화 이름만으로 V11 수준 이상의 한국어 단일 HTML 교본 CREATE/UPDATE를 요청할 수 있어야 한다. 아직 반복 실행 성능은 **검증 목표**이지 이미 입증한 결과가 아니다.
2. **개별 교본은 실험·검증 수단**, 주 개발 산출물은 다른 전문화에서도 재사용 가능한 **자료 해석법·설명 설계법·오류 예방법·품질 평가법**이다. 과거 V11 7개, 비전 CREATE, 생존 V1~V3.1은 모두 배울 수 있는 증거 자산이다.
3. GitHub는 공개 가능한 정책·사례·검증 도구·메타데이터·이력을 보관한다. 개인 V11 원본, 실제 사용자 HTML, 외부 장문 원문/번역은 공개하지 않는다. 사용자가 승인하지 않은 신규 HTML은 **검토본**이며 정본으로 승격하지 않는다.
4. 필요하면 기존 `engine/v2` 보존·기능 QA 도구를 활용하지만, **새 독립 AI API/OAuth/Codespaces/웹앱/거대 JSON 스키마를 선결 조건**으로 만들지 않는다. 도구 구축은 실제 품질·반복 작업 비용에 기여하는 증거가 있을 때만 재검토한다.

## 2. 출처 선택 — 확정 정책

- **사용자가 특정 공략·URL·파일을 지정하면 우선**한다. 다만 해당 자료의 패치/빌드/선택 특성 부적합이 확인되면 숨기지 않고 알려 검토한다.
- 사용자 지정이 없으면 **Wowhead의 해당 패치·전문화 공략 하나를 기본 편집 원문(단일 기준 출처)**으로 삼는다. 실제 공략의 우선순위·오프너·조건을 먼저 충분히 추출한다. 기존 우수 V11의 단일 Wowhead 방식이 이 정책의 주요 근거다.
- **다른 공략 사이트는 기본 필수 조건이 아니다.** Icy Veins, Method 등은 Wowhead의 일부 조건이 누락·불명확·상충하거나 게임 변경이 의심되는 경우에만 **해당 쟁점에 한정하여 보조 검증**한다. `최소 2개 사이트`, `반드시 3개 사이트`, `다수결` 규정은 적용하지 않는다.
- 공식 패치 노트/게임 내 주문 설명/검증된 주문 데이터 확인은 **기준 공략에 대한 사실·버전 검증**이다. 이를 다른 작성자의 전체 로테이션과 임의로 합치는 절차로 취급하지 않는다.
- 보조 공략의 우선순위와 오프너를 기준 공략과 **짜깁기하지 않는다**. 출처가 다를 때는 패치·날짜·영웅 특성·선택 특성·세트·대상 수·오프너/지속 딜 범위부터 확인하고 해결되지 않은 조건은 `REVIEW`로 보류한다.
- 여러 출처를 실제 사용했다면 **독립성**을 평가한다. URL/도메인 수가 곧 독립 증거 수가 아니다. 같은 작성자·파생 콘텐츠 등 계보가 겹칠 가능성을 확인하며, 확인하지 못했다면 독립성을 단정하지 않는다.
- 원문 수집 시 **원래 페이지의 선택형 특성 탭·접힌 표·조건부 단계·오프너 분기**가 텍스트 추출 후에도 보존되는지 확인한다. 서로 다른 빌드의 보이는 문자열을 한 순서로 합치지 않는다. 구조를 확정할 수 없으면 부분 미확인으로 남긴다.
- 이번 기준 출처 정책은 **더 많은 자료를 읽으면 언제나 더 좋다**는 가정을 배제한다. 추가 자료의 수집·분석도 해결할 불확실성과 예상 품질 기여가 명확할 때만 한다.

## 3. 제작·평가를 분리 — 확정 정책, 측정 방법은 발전 가능

### 제작

게임의 진짜 판단 문제를 `패치/빌드/상태 → 조건·임계값 → 행동·우선권 → 후속 상태 → 왜/예외 → 근거`로 이해한 **뒤** 교본 표현을 설계한다. 특정 전문화의 기술 로직을 다른 전문화에 이식하지 않는다. 설명은 전문화의 특징에 따라 표·원리·흐름·주의 박스를 선택한다. 장 수·행 수·툴팁 수를 고정하지 않는다.

### 결과물 평가(Q0–Q4)

| 차원 | 핵심 질문 | 적용 |
|---|---|---|
| Q0 사실 정확성 | 패치/기술/특성/조건·수치가 실제 근거와 부합하는가? | **필수**; 미검증 내용 승인 불가 |
| Q1 판단 정확성/완결성 | 전투 상태·상위 우선순위·오프너 상태 전이까지 고려해 다음 행동을 결정할 수 있는가? | **필수**; 확정 판단 오류 시 승인 보류 |
| Q2 이해·응용 가능성 | 독자가 이유/예외를 이해해 처음 보는 유사 상황에 적용할 수 있는가? | 독립 비교·사용자 평가 |
| Q3 실전 사용성 | 필요한 내용을 빠르게 찾고 모호함/중복 없이 사용할 수 있는가? | 독립 비교·사용자 평가 |
| Q4 변경 안정성 | 비대상 7개 V11 본문, 정당한 기존 규칙 및 UI 동작이 훼손되지 않았는가? | **필수**; 실제 바이트/기능 증거 |

- Q0/Q1/Q4 실패를 Q2/Q3의 좋은 점수로 상쇄하지 않는다. **의미 정확성·설명 효과·HTML 기능은 별개**다.
- 판정은 검증 범위에 따라 `통과 / 실패 / 부분 확인 / 미검증`으로 남긴다. 가중치 총점·글자 수·표 수·출처 수만으로 최종 품질을 결정하지 않는다.
- **고정 6개 반례 등 횟수 할당량은 폐지.** 전문화의 주요 빌드/영웅 특성 ON/OFF, 중첩·충전 임계, 상위 우선권, 오프너→지속 딜, 원리·요약·심화 간 중복 규칙을 **결정 분기별로** 선택해 시험한다. 사례의 수는 범위에 비례하며 검증하지 않은 가지를 명시한다.
- 평가의 **기대 행동은 교본을 베끼지 말고** 기준 출처·공식 사실 자료의 해당 조건에서 독립 도출한다. 근거의 범위가 부족하면 `판정 불능/REVIEW`이지 자동 PASS/FAIL이 아니다.
- 게임플레이 출처 대조 ≠ 시뮬레이션·실제 로그·개인 플레이 최적화 검증. 원본 보존/JS PASS ≠ 교본의 내용 PASS.

## 4. 개발 작업 자체의 품질 기여 게이트 — 확정 정책

모든 새 기능/정책/수정/자료 확장은 실행 전에 다음을 짧게 검토한다.

1. **해결할 실제 문제:** 독자의 어떤 판단·이해 또는 반복 제작 과정에 결함이 있는가?
2. **개선 가설과 대안:** 왜 제안한 변경이 도움이 되는가? 더 적은 수정/더 적은 출처로 해결 가능한가?
3. **측정 가능한 비교:** 변경 전 오류 사례(**양성 대조**)와 정상 사례(**오탐 방어**), 새 조건/오프너 회귀를 어떻게 확인할 것인가?
4. **실행 범위:** 의미 검증 없이 국소 패치·코드 확장을 반복하지 않는다. 개인 정본은 승인 없이 교체하지 않는다.
5. **결과 판정:** `개선 확인 / 개선 불확실 / 품질 저하`. 주장할 수 있는 증거 수준을 명시한다.
6. **범용 기여:** 결함의 구체적인 기술명 대신 실패 원인, 탐지 규칙, 검증 반례, 적용 경계, 다른 전문화에 전이 가능한 지식을 남긴다.

**실행 규칙:** 실질 기여가 불분명하면 사용자에게 도움이 되는 최소 검증만 실시한다. `개발 가능하다`, `CI가 녹색이다`, `설명량이 증가했다`는 단독 실행·품질 향상 근거가 아니다.

**모든 이슈의 범용성 판단을 항상 수행:** (a) 개별 전문화/패치의 일회성 조건인가, (b) 기존 Wowhead 기본 출처+필요한 쟁점만 보조 검증하는 절차로 해결 가능한가, (c) 여러 전문화에서 재현되는 동일한 **실패 원인**인가, (d) 일반화할 경우 정상 사례를 오탐하는 위험은 없는가를 **짧게 판단**한다. 결론이 일회성·기존 정책으로 해결 가능이면 해당 규칙만 수정/근거 보완하고 **새 검사기·스키마·프로세스는 만들지 않는다**. 공통 문제라면 '상태/조건/행동/출처 검증법'처럼 전이 가능한 최소 원칙만 남긴다. **매번 범용화를 검토하되, 매번 새로운 범용 구조를 개발하지는 않는다.**

## 5. 과거 지식 재사용과 일반화의 한계 — 확정 정책

- 기존 7개 V11은 **우수한 비교 기준**이지 게임 로직/형식의 절대 불변 진리가 아니다. **좋은 이유**(어떤 상태 판단을 가능하게 하는지)를 추출하며 형식은 복제하지 않는다.
- 생존 V1/V2는 재사용 초안이 아닌 **실패 반례**; V3/V3.1은 일부 개선의 검증 자료이며 사용자 최종 승인 정본이 아니다. 비전은 HTML 원형 보존·출처 검토 단계 구분의 성과와 의미 검증 미완의 사례다.
- 실패 사례뿐 아니라 **정상 사례(음성 대조)**를 반드시 유지한다. CSS 클래스/기술명 문자열 일치만으로 오류를 확정하지 않는다.
- 배운 지식은 `발견 → 원인 분석 → 범용 원칙 제안 → 과거 양성·음성 대조 → 새 전문화 독립 검증 → 반복 제작 실증` 순서로 성숙도를 표시한다. 앞 단계만 통과한 원칙을 반복 품질 개선 완료로 승격하지 않는다.
- **한 전문화에서만 유효한 특성·수치·게임 상태를 범용 규칙으로 강제하지 않는다.** 범용화할 것은 분석·설명·검증 방법이고, 전문화 고유 분기는 존중한다.
- 새 전문화의 시험은 **실제 교본을 만들 필요 없이** 원문의 전제·조건 분기를 선별 추출해 규칙/평가법의 유효성을 검토할 수 있다. 이 시험을 완성 교본 실증이나 사용자 품질 승인으로 과장하지 않는다.

## 6. 정책과 실험 기록의 경계 및 변경 규칙

- **확정 정책:** 이 문서 및 사용자가 승인한 방향. 작업 중 발견한 한두 개 사례는 **잠정 인사이트/검증 가설**로 별도 기록하고 자동 정책화하지 않는다.
- **실험/증거:** [QUALITY_GENERALIZATION_CASEBOOK](QUALITY_GENERALIZATION_CASEBOOK.md)에 관측, 근거 범위, 반례, 반증 가능성, 검증 상태를 기록한다. 출처 작성자 일치·선택형 페이지 추출 문제 등 개별 조사 사실이 미확인이면 검증된 사실처럼 쓰지 않는다.
- 세부 실행 순서는 [EDITORIAL_QUALITY_PROTOCOL](EDITORIAL_QUALITY_PROTOCOL.md) 및 [CHAT_FIRST_PLAYBOOK](CHAT_FIRST_PLAYBOOK.md), 원문 정책은 [SOURCE_ACQUISITION](SOURCE_ACQUISITION.md)을 따른다. **이 최상위 정책과 충돌하는 과거 필수 사이트 수·고정 반례 수·고정 HTML 구성요소 수는 현재 운영 규정으로 사용하지 않는다.**
- 정책 개정 시 무엇을 대체하는지, 이유, 기대 품질 효과, 부작용/오탐 위험, 실제 검증 결과를 기록한다. 과거 시범·엔진 코드·ADR은 삭제하지 않고 **역사적 계약**으로 보존한다.
- 공개 GitHub에는 정책·규칙 메타데이터·검증 결과만. 사용자 개인 HTML 원문, 외부 공략의 대량 재배포, 무단 정본 변경·`main` merge·Pages 발행은 금지한다.

**적용 예시:** 고양 주술사에서 복수 사이트의 작성자/원문 분기 문제를 발견했다는 초기 시험 기록은 이 정책을 **보강하는 검증 가설**이다. 해당 전문화의 우선순위 게임플레이 전체 정확성이나 범용 방법론의 독립 재현성이 검증됐다는 뜻이 아니다.
