# QUALITY_FIRST_POLICY — 범용 교본 제작·검증 최상위 정책

> **2026-11-11 사용자 논의로 확정된 운영 원칙.** 범위: ROTATION TEXTBOOK / Chat-first 교본 제작 방법론. 개인 HTML·외부 공략 원문은 공개 GitHub에 보관하지 않는다. 과거 독립 AI 자동화 제품 개발을 재개하라는 지침이 아니다.
>
> **우선순위:** 개별 전문화 보완이나 기능 개발 < 다른 전문화에도 전이되는 제작 지식·평가 방법 < 실제 독자의 게임 판단·이해에 대한 검증 가능한 기여.

## 0. 사용자 확정 최상위 방향 — 교본 완성 중심, 미시 개발의 목적화 금지 (2026-11-13)

**이 절은 신규·수정·분석·테스트·GitHub 개발·새 채팅 인계에 모두 적용하는 상위 작업 판단 기준이다.** 기존의 상세 지침이나 전문화별 조사 기록이 이 원칙과 충돌하면 **사용자에게 전달할 실제 교본의 품질**을 먼저 지킨다.

**최종 제품은 특정 전문화를 입력하면 공략 원문을 누락 없이 이해·구조화해 V11 수준 이상의 실제 사용 가능한 한국어 단일 HTML 교본을 CREATE/UPDATE하는 경험**이다. GitHub 정책, 추출기, 상태 전이 QA, CI는 이 경험을 안정적으로 반복하게 만드는 **보조 자산**이다. 개별 교본을 만들고 품질을 비교하는 것은 핵심 검증 경로이지, 도구 개발을 계속하기 위한 구실이 아니다.

1. **매 작업의 최우선 질문:** “이번 작업은 *어떤 전문화에도 적용 가능한 원문 이해 → 상태·조건·행동 분석 → 실전 교본 작성 → 정확성/사용성 검증* 중 어느 단계의 실질적인 품질 문제를 해결하는가?” 한 문장으로 설명하지 못하면 개발 범위를 넓히지 않는다.
2. **기본 우선순위:** (A) 최신 패치/특성에 맞는 실제 원문과 숨은 조건을 충분히 확보, (B) 해당 전문화의 게임 판단 논리를 손실 없이 구조화, (C) 독자가 즉시 사용할 수 있는 V11 이상 교본 작성, (D) 내용 Q0/Q1·가독성 Q2/Q3·HTML 보존 Q4 확인 및 다른 전문화 재적용. 각각은 목적을 위해 필요한 범위만 수행한다. **C를 오랫동안 미룬 채 A·B·D의 검사기만 증식시키지 않는다.**
3. **개별 이슈의 종료 원칙:** 선택 ID 1개, 물약 1종, 특정 빌드 분기 등은 *실제 다음 행동이 달라지거나 교본의 중요한 내용이 빠지는지*까지 확인한다. 원인이 기존 절차로 해결되거나 근거 부족으로 REVIEW가 적절하면 해당 이슈 조사를 멈추고 상위 제작 과정으로 복귀한다. **미확정 사실을 추측해 메우지 않는 것도 올바른 종료**다.
4. **새 도구·스키마·테스트의 엄격한 도입 기준:** 여러 전문화에 재발할 **입증된 원인**과 기존 자산으로 해결할 수 없는 **구체적인 품질 결함**이 있으며, 최소 변경으로 이를 방지할 때만 만든다. 테스트 수·커밋 수·코드량·원문 메타데이터 수집량·상세 감사 기록 수는 **성과 지표가 아니다**. 단순 수정·수동 대조·기존 도구 재사용이 충분하면 새 도구를 만들지 않는다.
5. **품질 평가의 기본 단위는 완성된 교본:** 단일·광역 지속 딜/오프너, 우선순위의 순위·행동·조건, 메커니즘·수치·이유·예외·영웅/특성 차이, 정확한 한국어 기술명, 요약과 심화의 일관성, 기존 HTML UX/보존을 실제 결과로 비교한다. 구조 수집 PASS나 CI PASS를 교본의 정확성·완성도로 승격하지 않는다.
6. **범용화는 방법에 적용하고 전문화 지식을 고정하지 않는다:** 실제 서로 다른 전문화의 **정상·실패 사례**에서 원인과 오탐을 재검증한다. 특정 전문화에만 있는 물약 수·영웅 특성·GCD 순서는 범용 규격으로 강제하지 않는다. 교본 구조도 고정하지 않고 **명확한 행동 결정에 도움이 되는 형식**을 선택한다.
7. **인계와 시작 시 적용:** 새 채팅은 최신 GitHub 활성 브랜치의 **이 절을 가장 먼저 읽고**, [CHAT_FIRST_PROJECT_INSTRUCTIONS](CHAT_FIRST_PROJECT_INSTRUCTIONS.md) → [HANDOFF_CHAT_FIRST_CURRENT](HANDOFF_CHAT_FIRST_CURRENT.md) → [CHAT_FIRST_PLAYBOOK](CHAT_FIRST_PLAYBOOK.md) 순으로 현재 상태와 다음 작업의 *교본 품질 기여*를 판단한다. 장황한 과거 전문화별 테스트 수를 다음 작업의 우선순위로 자동 승계하지 않는다. 중요한 연구 사실·미검증 항목은 기록으로 남기되, 다음 단계는 **가능한 한 실제 교본 제작 전체 흐름**에 연결한다.

**진행/중단 결정:** 구체적 최종 교본 개선 효과가 확인되면 계속한다. 하나의 예외 조사만 반복하거나 새 구현을 쌓아도 교본 완성·재현성에 가까워지지 않으면 **그 작업을 정지하고 가장 작은 종단 간 교본 제작/평가로 돌아간다.** 이는 자료 완전성·Q0/Q1 사실 정확성 게이트를 생략하라는 뜻이 아니다.

## 0.1 사용자 화면의 한국어 표기·용어 표준 (2026-11-14 사용자 확정)

**사용자 화면에는 자연스럽고 즉시 이해할 수 있는 한국어만 표시한다.** `balance-keeper-st-in-2` 같은 내부 규칙 키, snake_case/kebab-case, 데이터 필드명, 원시 주문 식별 번호, 아이콘 파일명, 영문 약어를 화면에 노출하지 않는다. 이 값들은 숨겨진 JSON·HTML data-* 속성·출처 메타데이터에서만 유지한다.

- **전문화 자원·상태의 짧은 한국어 표기:** 천공의 힘 → **천힘**, 재사용 대기시간 → **쿨**, 전역 재사용 대기시간 → **전역 쿨**, 공격 가능한 적 수 → **대상 수**, 지속 피해 효과 → **지속 피해**, Proc → **발동**, Buff → **강화 효과**, Debuff → **약화 효과**, ST → **단일**, AoE → **광역**. 이 매핑은 문서에서 의미가 실제로 같은 경우에만 사용한다.
- **첫 등장 정의:** 빠른 참조의 첫 용어 설명에서 `천힘: 천공의 힘 · 쿨: 재사용 대기시간 · 전역 쿨: 전역 재사용 대기시간 · 대상 수: 공격 가능한 적 수`처럼 한 번 정의한다. 이후 표·조건·툴팁에서는 짧은 한국어 표기를 사용한다.
- **수식 유지:** `대상 수 ≥ 4`, `천힘 ≥ 90`, `쿨 ≤ 15초`, `A ∧ B`, `A ∨ B`처럼 수치·비교 연산자·논리 구조는 유지하되, 변수와 상태 이름은 한국어로 쓴다. 의미가 불명확해지면 축약하지 않고 전체 한국어를 쓴다.
- **기술·강화 효과 명칭과 아이콘(2026-11-14 사용자 REVIEW 재확인):** 게임 내 공식 한국어 기술명·강화/약화 효과명을 우선하고 임의 번역·축약 금지. **트래킹 가능한 기술·발동·버프·디버프 명칭이 실제 읽히는 모든 위치**(첫 화면, 우선순위 행동·조건, 원리, 오프너, 제목·본문·심화 사례, 설명 툴팁)에는 **확인된 해당 아이콘과 이름을 한 요소로 연결**한다. 개별 명칭이 처음 등장했을 때만 붙이고 뒤에서는 생략하는 방식은 금지. 이미 다른 전문화에 확인된 동명의 아이콘이라도 주문/효과 ID·맥락이 다르면 그대로 추정해서 재사용하지 않는다. 아이콘의 실제 신원이 불명확하면 추측해 대체하지 않고 REVIEW 처리한다. 영문 원문 기술명·아이콘 파일명은 내부 출처 자료에만 남긴다.
- **상태·검증 표기:** REVIEW/PASS, Q0/Q1/Q4, API, UI 등 내부 검증 용어는 화면에 표시하지 않는다. `확인 중`, `확인 완료`, `게임 판단 정확성`, `화면 기능`처럼 자연스러운 한국어로 쓴다.
- **브랜드·출처:** Wowhead/Blizzard는 화면에서 `와우헤드`/`블리자드`로 표기한다. 원문 출처·패치·갱신일은 한국어 문장으로 간결히 표시한다.
- **범위:** 새로 만들거나 수정하는 전문화의 모든 사용자 표시 영역(첫 화면, 우선순위, 오프너, 선택 특성, 툴팁, 심화 예제, 목차·선택 메뉴)에 적용한다. 기존 V11 7개 원본 본문은 사용자가 별도 UPDATE를 요청하지 않은 한 임의로 일괄 번역·재작성하지 않는다.
- **검증:** HTML에서 스크립트·스타일·숨겨진 내부 데이터는 제외하고, 실제 표시되는 모든 텍스트 노드와 title/aria-label/툴팁 문자열에 영문 약어·내부 키·아이콘 파일명이 없는지 확인한다. 기능·게임 판단 정확성 검증은 별도 보고한다.
## 1. 최종 목표와 역할 — 확정 정책

1. 사용자는 ChatGPT에서 전문화 이름만으로 V11 수준 이상의 한국어 단일 HTML 교본 CREATE/UPDATE를 요청할 수 있어야 한다. 아직 반복 실행 성능은 **검증 목표**이지 이미 입증한 결과가 아니다.
2. **개별 교본은 사용자에게 전달할 최종 제품이자 제작법의 검증 수단**이다. 반복 개발의 핵심 축적 자산은 다른 전문화에서도 재사용 가능한 **자료 해석법·설명 설계법·오류 예방법·품질 평가법**이다. 방법론 개발이 실제 교본 완성보다 우선해서는 안 된다. 과거 V11 7개, 비전 CREATE, 생존 V1~V3.1은 모두 배울 수 있는 증거 자산이다.
3. GitHub는 공개 가능한 정책·사례·검증 도구·메타데이터·이력을 보관한다. 개인 V11 원본, 실제 사용자 HTML, 외부 장문 원문/번역은 공개하지 않는다. 사용자가 승인하지 않은 신규 HTML은 **검토본**이며 정본으로 승격하지 않는다.
4. 필요하면 기존 `engine/v2` 보존·기능 QA 도구를 활용하지만, **새 독립 AI API/OAuth/Codespaces/웹앱/거대 JSON 스키마를 선결 조건**으로 만들지 않는다. 도구 구축은 실제 품질·반복 작업 비용에 기여하는 증거가 있을 때만 재검토한다.

## 2. 출처 선택 — 확정 정책

- **사용자가 특정 공략·URL·파일을 지정하면 우선**한다. 다만 해당 자료의 패치/빌드/선택 특성 부적합이 확인되면 숨기지 않고 알려 검토한다.
- 사용자 지정이 없으면 **Wowhead의 해당 패치·전문화 공략 하나를 기본 편집 원문(단일 기준 출처)**으로 삼는다. 실제 공략의 우선순위·오프너·조건을 먼저 충분히 추출한다. 기존 우수 V11의 단일 Wowhead 방식이 이 정책의 주요 근거다.
- **다른 공략 사이트는 기본 필수 조건이 아니다.** Icy Veins, Method 등은 Wowhead의 일부 조건이 누락·불명확·상충하거나 게임 변경이 의심되는 경우에만 **해당 쟁점에 한정하여 보조 검증**한다. `최소 2개 사이트`, `반드시 3개 사이트`, `다수결` 규정은 적용하지 않는다.
- 공식 패치 노트/게임 내 주문 설명/검증된 주문 데이터 확인은 **기준 공략에 대한 사실·버전 검증**이다. 이를 다른 작성자의 전체 로테이션과 임의로 합치는 절차로 취급하지 않는다.
- 보조 공략의 우선순위와 오프너를 기준 공략과 **짜깁기하지 않는다**. 출처가 다를 때는 패치·날짜·영웅 특성·선택 특성·세트·대상 수·오프너/지속 딜 범위부터 확인하고 해결되지 않은 조건은 `REVIEW`로 보류한다.
- 여러 출처를 실제 사용했다면 **독립성**을 평가한다. URL/도메인 수가 곧 독립 증거 수가 아니다. 같은 작성자·파생 콘텐츠 등 계보가 겹칠 가능성을 확인하며, 확인하지 못했다면 독립성을 단정하지 않는다.
- **필수 원문 확보 게이트(모든 전문화):** 기본 표시 콘텐츠 외에 마스터/영웅 특성·전투 유형·빌드/선택 특성·지역 탭·오프너의 기술 순서·물약 사용 시점·쿨다운·접힌 Notes/Further/Advanced·타임라인·모든 실제 관련 `?`/hover 팁의 **내용을 전수 확보**한다. 상위 선택을 바꾼 뒤 새로운 하위 항목도 조사하고, 영웅 특성·전투 유형·특성 등으로 실제 달라지는 오프너의 순서를 보존한다. **물약·아이템·특성의 선택은 실제 원문의 조건에 따라 판단한다.** 선택에 따라 기술 사용 순서·사용 시점·선시전 여부가 달라지면 해당 선택은 **실제 오프너 분기**로 기록하고, 행동이 변하지 않으면 공통 `물약 사용` 슬롯 또는 단순 예시로 통합할 수 있다. 특정 물약명을 일률적으로 필수 소비재로 단정하거나, 여러 물약을 하나의 시퀀스에서 연이어 사용하게 해서는 안 된다. **고양 주술사 12.1.5 실제 저장본**은 영웅 특성·ST/AoE·물약 3종에 따른 12개 시퀀스와 폭풍인도자 AoE의 낙뢰 선시전 차이를 확인한 반례이며, 모든 전문화에 동일 분기를 강제하는 근거는 아니다. [실제 사용자 저장본 검증](ENHANCEMENT_SAVED_HTML_EVIDENCE_20261112.md). 각 팁은 가능하면 **어느 영웅/전투 탭·섹션·표/행·인접 기술 옆인지** 위치 단서와 주변 문맥을 함께 기록한다. **정확한 DOM ID·대상 순위 행의 연결을 전수 입증하는 것은 확보 게이트의 필수 조건이 아니다.** 이후 ChatGPT가 의미 관계를 해석하고, 적용 대상이 모호하거나 행동이 바뀔 때만 원본 관계를 추가 검증한다. 핵심 본문 누락·패치 불일치·분기 혼합은 여전히 Gate A FAIL. [SOURCE_ACQUISITION](SOURCE_ACQUISITION.md) 참조. **원문은 충실하게 확보하고, 교본은 정확하고 간결하게 집필한다.**
**상위 정책 정정(2026-11-12):** 2026-11-11 당시의 단일 `물약 사용` 슬롯 선호보다 **원문에서 확인된 행동 분기**가 우선한다. 실제 조건부 원문으로 행동 변화가 확인된 경우 물약 선택을 접거나 생략하지 않는다. 분기 여부가 불확실하면 추측해 단순화하지 않고 Q0/Q1 검토로 남긴다.

**범위 완전성의 필수 판정:** 영웅별 Notes·모든 실제 관련 `?`의 설명 **본문**·오프너 내 물약 사용 타이밍(특정 물약명은 예시)·상위 선택 뒤 나타난 하위 탭·접힌 설명은 모두 필수 수집 대상이다. 내용은 확보했으나 팁 위치/행 귀속이 불명확하면 `본문 확보·위치 미확인`으로 기록하며 **그 사실만으로 Gate A를 실패 처리하지 않는다.** 의미 분석에서 중요한 다음 행동이 여러 해석에 따라 달라진다면 Q0/Q1 REVIEW로 별도 보류하고 필요한 연결만 추가 검증한다. 본문 누락이나 영웅/전투/빌드별 핵심 시퀀스가 섞여 있어 실제 내용을 알 수 없다면 Gate A 미통과 및 부분 검토본. 자료 누락과 최종 집필의 의도적 축약을 구별한다.
- 이번 기준 출처 정책은 **더 많은 자료를 읽으면 언제나 더 좋다**는 가정을 배제한다. 추가 자료의 수집·분석도 해결할 불확실성과 예상 품질 기여가 명확할 때만 한다.

## 3. 제작·평가를 분리 — 확정 정책, 측정 방법은 발전 가능

### 제작

게임의 진짜 판단 문제를 `패치/빌드/상태 → 조건·임계값 → 행동·우선권 → 후속 상태 → 왜/예외 → 근거`로 이해한 **뒤** 교본 표현을 설계한다. 특정 전문화의 기술 로직을 다른 전문화에 이식하지 않는다. 설명은 전문화의 특징에 따라 표·원리·흐름·주의 박스를 선택한다. 장 수·행 수·툴팁 수를 고정하지 않는다.

**실전 표현 정책(사용자 확정 선호):** 기본 운용은 `상태·수치·조건 → 행동`을 짧게 표시한다. 자연스러운 경우 변수 정의, 부등호, 수치 계산, A/B 분기를 활용한다. **압축은 핵심 정보 보존을 전제로 한다.** 기호·약어는 첫 사용 전 의미·단위·범위를 명시한다. 핵심 자원·강화·발동의 생성/소비/수치/행동 연결은 교본의 필수 기초이며 생략하지 않는다. 일반론·중복 문장을 줄이고 자원 관리·고급 팁·우선순위 예외를 이해하는 데 필요한 배경은 남긴다. 근거 없는 수치나 기계적인 수식화는 금지하며, 짧아졌다는 사실을 정확성의 증명으로 삼지 않는다. 시각 표현은 기존 V11 공통 서식을 기본으로 재사용하고 실제 주문 아이콘 및 링크 텍스트의 기준선·글자 크기·줄 높이를 통일한다. **우선순위와 순차 시전의 표기·의미를 구별**하고 처음에 짧게 정의한다. 여러 메커니즘을 한 긴 문단에 몰지 않고 작동/발동/효과/예외처럼 의미 단위의 짧은 목록으로 나눈다(필요한 경우 표·문장 사용 가능). 설명의 참조는 실제 장·표 제목 또는 내부 링크를 사용한다. 예외에는 적용·미적용 상태와 행동을 함께 제시하고, 원문이 최적 임계값을 지정하지 않으면 구체적인 안전 판단 예시와 미확인 범위를 구분한다. 불필요한 독립 CSS는 피하되 비대상 교본 본문은 승인 없이 변경하지 않는다. 공통 접기/펼치기 메뉴는 직업·전문화가 추가되어도 밀도가 유지되도록 한 줄에 짧게 배치한다.

### 결과물 평가(Q0–Q4)

| 차원 | 핵심 질문 | 적용 |
|---|---|---|
| Q0 사실 정확성 | 패치/기술/특성/조건·수치가 실제 근거와 부합하는가? | **필수**; 미검증 내용 승인 불가 |
| Q1 판단 정확성/완결성 | 전투 상태·상위 우선순위·오프너 상태 전이까지 고려해 다음 행동을 결정할 수 있는가? | **필수**; 확정 판단 오류 시 승인 보류 |
| Q2 이해·응용 가능성 | 독자가 이유/예외를 이해해 처음 보는 유사 상황에 적용할 수 있는가? | 독립 비교·사용자 평가 |
| Q3 실전 사용성 | 필요한 내용을 빠르게 찾고 모호함/중복 없이 사용할 수 있는가? | 독립 비교·사용자 평가 |
| Q4 변경 안정성 | 비대상 7개 V11 본문, 정당한 기존 규칙 및 UI 동작이 훼손되지 않았는가? | **필수**; 실제 바이트/기능 증거 |

- Q0/Q1/Q4 실패를 Q2/Q3의 좋은 점수로 상쇄하지 않는다. **의미 정확성·설명 효과·HTML 기능은 별개**다.
- 판정은 검증 범위에 따라 `통과 / 실패 / 부분 확인 / 미검증`으로 남긴다. 가중치 총점·글자 수·표 수·출처 수만으로 최종 품질을 결정하지 않는다.
- **고정 6개 반례 등 횟수 할당량은 폐지.** 전문화의 주요 빌드/영웅 특성 ON/OFF, 중첩·충전 임계, 상위 우선권, 오프너→지속 딜, 원리·요약·심화 간 중복 규칙을 **결정 분기별로** 선택해 시험한다. 사례의 수는 범위에 비례하며 검증하지 않은 가지를 명시한다.
- 평가의 **기대 행동은 교본을 베끼지 말고** 기준 출처·공식 사실 자료의 해당 조건에서 독립 도출한다. 근거의 범위가 부족하면 `판정 불능/REVIEW`이지 자동 PASS/FAIL이 아니다.
- 게임플레이 출처 대조 ≠ 시뮬레이션·실제 로그·개인 플레이 최적화 검증. 원본 보존/JS PASS ≠ 교본의 내용 PASS.

## 4. 개발 작업 자체의 품질 기여 게이트 — 확정 정책

모든 새 기능/정책/수정/자료 확장은 실행 전에 다음을 짧게 검토한다.

1. **해결할 실제 문제:** 독자의 어떤 판단·이해 또는 반복 제작 과정에 결함이 있는가?
2. **개선 가설과 대안:** 왜 제안한 변경이 도움이 되는가? 더 적은 수정/더 적은 출처로 해결 가능한가?
3. **측정 가능한 비교:** 변경 전 오류 사례(**양성 대조**)와 정상 사례(**오탐 방어**), 새 조건/오프너 회귀를 어떻게 확인할 것인가?
4. **실행 범위:** 의미 검증 없이 국소 패치·코드 확장을 반복하지 않는다. 개인 정본은 승인 없이 교체하지 않는다.
5. **결과 판정:** `개선 확인 / 개선 불확실 / 품질 저하`. 주장할 수 있는 증거 수준을 명시한다.
6. **범용 기여:** 결함의 구체적인 기술명 대신 실패 원인, 탐지 규칙, 검증 반례, 적용 경계, 다른 전문화에 전이 가능한 지식을 남긴다.

**실행 규칙:** 실질 기여가 불분명하면 사용자에게 도움이 되는 최소 검증만 실시한다. `개발 가능하다`, `CI가 녹색이다`, `설명량이 증가했다`는 단독 실행·품질 향상 근거가 아니다.

**모든 이슈의 범용성 판단을 항상 수행:** (a) 개별 전문화/패치의 일회성 조건인가, (b) 기존 Wowhead 기본 출처+필요한 쟁점만 보조 검증하는 절차로 해결 가능한가, (c) 여러 전문화에서 재현되는 동일한 **실패 원인**인가, (d) 일반화할 경우 정상 사례를 오탐하는 위험은 없는가를 **짧게 판단**한다. 결론이 일회성·기존 정책으로 해결 가능이면 해당 규칙만 수정/근거 보완하고 **새 검사기·스키마·프로세스는 만들지 않는다**. 공통 문제라면 '상태/조건/행동/출처 검증법'처럼 전이 가능한 최소 원칙만 남긴다. **매번 범용화를 검토하되, 매번 새로운 범용 구조를 개발하지는 않는다.**

## 5. 과거 지식 재사용과 일반화의 한계 — 확정 정책

### 5.1. 기준본의 종류를 먼저 구별한다 — 실패본 복제 금지 (2026-11-13 사용자 재확인)

**사용자 평가에서 드러난 근본 원인:** 고양 V3.x/후속 V11 형식 덧칠이 비전보다 읽기 어려웠던 이유는 **이미 잘못된 표·정보 위계·본문을 기준으로 다음 버전을 제작했기 때문**이다. 기존 파일의 디자인·텍스트를 부분 수정하면 그 실패 원인도 계승한다. 이는 단순 CSS가 아니라 **기준본 선정과 제작 경로**의 오류다.

- **게임 내용의 기준본:** 사용자 지정 자료가 있으면 우선, 없으면 **같은 패치/빌드의 최신 Wowhead 공략 원문 1개**에서 상태·조건·행동·이유·예외를 새로 추출한다. 이전 미승인 교본/JSON을 게임 내용의 정본으로 자동 재사용하지 않는다. 출처 원문이 전부 확보되지 않았으면 미확인 부분을 REVIEW로 두고 게임 규칙을 지어내지 않는다.
- **시각·독해의 기준본:** 기존 V11 7개 정상군과 사용자에게 **비교적 좋은 평가를 받은 비전 및 고양 제로베이스**의 정보 역할을 참고한다. 단, 비전/고양의 게임 내용은 아직 미승인이며 사용자 표현 평가는 **모든 전문화에 적용되는 무조건적 최종 승인**이 아니다. 공통 정보 역할(한눈에 보기, 우선순위, 판단 이유 공개, 특수 `?`, 오프너 순서, 접이식 메뉴)을 재사용하되 장 수·행 수·조건을 강제하지 않는다.
- **실패본의 사용 범위:** 사용자가 가독성/구조를 반려한 고양 V3.x 및 이를 재배치한 Cross-spec HTML 등은 **실패 이유 분석·전후 비교·회귀 반례**로만 사용한다. 신규 CREATE 또는 구조적 재작성의 출처, UI 템플릿, 데이터 기본값으로 삼지 않는다.
- **UPDATE 예외:** 사용자가 이미 승인한 정상 교본을 유지·부분 수정할 때에는 기존 본문/UI를 보호하면서 **새 기준 원문의 차이만** 반영한다. 모든 UPDATE를 무조건 제로베이스로 하거나 정상 자산을 불필요하게 폐기하는 것도 잘못이다.
- **기준본 선택의 순서:** (1) 이번 작업에서 재사용하려는 파일이 **원문·승인된 결과·참고 시범·반려된 실패본** 중 무엇인지 확인 → (2) 내용 기준과 표현 기준을 **별개로 선정** → (3) 실제 독자의 다음 행동/정보 가독성에 근거한 선택인지 확인 → (4) 그 다음에 표·HTML 제작. 기존 엔진/JSON/템플릿의 존재 자체는 승인 근거가 아니다.

**구현 반영:** `engine/v2/create_guide.py`의 개인 CREATE 실행 경로는 기존 비전 `arcane.json` 수기 초안을 더 이상 **묵시적 기본 입력으로 사용하지 않으며**, 새 제작에는 `canonical_priority_rules` 명시를 요구한다. 과거 초안의 HTML은 `--legacy-review-only`에서만 재현할 수 있고 결과를 **역사적 비교·미승인**으로 표시한다. 이는 원문 내용이 실제로 정확함을 자동 확인하는 기능이 아니라, **불량 기준본의 자동 승계를 차단하는 좁은 가드**다.


- 기존 7개 V11은 **우수한 비교 기준**이지 게임 로직/형식의 절대 불변 진리가 아니다. **좋은 이유**(어떤 상태 판단을 가능하게 하는지)를 추출하며 형식은 복제하지 않는다.
- 생존 V1/V2는 재사용 초안이 아닌 **실패 반례**; V3/V3.1은 일부 개선의 검증 자료이며 사용자 최종 승인 정본이 아니다. 비전은 HTML 원형 보존·출처 검토 단계 구분의 성과와 의미 검증 미완의 사례다.
- 실패 사례뿐 아니라 **정상 사례(음성 대조)**를 반드시 유지한다. CSS 클래스/기술명 문자열 일치만으로 오류를 확정하지 않는다.
- 배운 지식은 `발견 → 원인 분석 → 범용 원칙 제안 → 과거 양성·음성 대조 → 새 전문화 독립 검증 → 반복 제작 실증` 순서로 성숙도를 표시한다. 앞 단계만 통과한 원칙을 반복 품질 개선 완료로 승격하지 않는다.
- **한 전문화에서만 유효한 특성·수치·게임 상태를 범용 규칙으로 강제하지 않는다.** 범용화할 것은 분석·설명·검증 방법이고, 전문화 고유 분기는 존중한다.
- 새 전문화의 시험은 **실제 교본을 만들 필요 없이** 원문의 전제·조건 분기를 선별 추출해 규칙/평가법의 유효성을 검토할 수 있다. 이 시험을 완성 교본 실증이나 사용자 품질 승인으로 과장하지 않는다.

## 6. 정책과 실험 기록의 경계 및 변경 규칙

- **확정 정책:** 이 문서 및 사용자가 승인한 방향. 작업 중 발견한 한두 개 사례는 **잠정 인사이트/검증 가설**로 별도 기록하고 자동 정책화하지 않는다.
- **실험/증거:** [QUALITY_GENERALIZATION_CASEBOOK](QUALITY_GENERALIZATION_CASEBOOK.md)에 관측, 근거 범위, 반례, 반증 가능성, 검증 상태를 기록한다. 출처 작성자 일치·선택형 페이지 추출 문제 등 개별 조사 사실이 미확인이면 검증된 사실처럼 쓰지 않는다.
- 세부 실행 순서는 [EDITORIAL_QUALITY_PROTOCOL](EDITORIAL_QUALITY_PROTOCOL.md) 및 [CHAT_FIRST_PLAYBOOK](CHAT_FIRST_PLAYBOOK.md), 원문 정책은 [SOURCE_ACQUISITION](SOURCE_ACQUISITION.md)을 따른다. **이 최상위 정책과 충돌하는 과거 필수 사이트 수·고정 반례 수·고정 HTML 구성요소 수는 현재 운영 규정으로 사용하지 않는다.**
- 정책 개정 시 무엇을 대체하는지, 이유, 기대 품질 효과, 부작용/오탐 위험, 실제 검증 결과를 기록한다. 과거 시범·엔진 코드·ADR은 삭제하지 않고 **역사적 계약**으로 보존한다.
- 공개 GitHub에는 정책·규칙 메타데이터·검증 결과만. 사용자 개인 HTML 원문, 외부 공략의 대량 재배포, 무단 정본 변경·`main` merge·Pages 발행은 금지한다.

**적용 예시:** 고양 주술사에서 복수 사이트의 작성자/원문 분기 문제를 발견했다는 초기 시험 기록은 이 정책을 **보강하는 검증 가설**이다. 해당 전문화의 우선순위 게임플레이 전체 정확성이나 범용 방법론의 독립 재현성이 검증됐다는 뜻이 아니다.


**2026-11-12 원문 조건 범위 재검증:** 고양 사용자가 저장한 12.1.5 원문의 선택 조건 82개는 62개 짝이 확인된 컨테이너 조건과 20개 독립 custom 마커로 **전부 보존**되었다. 물약·영웅 선택의 실제 시전 행동 분기 여부는 각 마커와 원문 단계 문맥을 ChatGPT가 함께 판단해야 한다. 관련 원문 조건 누락을 원천 예방하며 자동 게임플레이 확정은 하지 않는다. [범위별 감사](WHML_SCOPE_EVIDENCE_20261112.md).
