# EDITORIAL QUALITY PROTOCOL — 결정 가능성 우선 교본 집필 규격 (2026-11-11)

> **우선순위: 자료 충실도 → 시전 판단 가능성 → 예외·원인 설명 → 사용자 경험 → HTML 무결성.**
> 이 문서는 ChatGPT가 반복 제작할 때 실제 교본 품질이 높아지도록 하는 콘텐츠 제작 절차다. 고정 장 수/문장 수/템플릿의 통과를 제품 성공으로 오인하지 않는다. **운영 우선순위·기본 Wowhead 단일 출처·Q0~Q4와 변경 기여 평가는 [QUALITY_FIRST_POLICY](QUALITY_FIRST_POLICY.md)를 우선 적용한다.**

## 1. 실패 원인과 수정 방향

- **Template-first 실패:** 이전 생존 초안은 먼저 `priority(action, reason)`의 2열 데이터로 원문을 분배했다. 실전의 3원소 **순위/행동/조건**이 분리되지 않으므로 수치·발동 조건이 글 속으로 묻혔다. → **규칙부터 적고 그 규칙을 표현할 UI를 나중에 선택한다.**
- **출처 혼합 실패:** 한 패치/하나의 실제 특성 분기를 고정하지 않고 Wowhead·Icy Veins·Method의 시점을 섞었다. 예를 들어 옛 `Flamefang Pitch`가 목록에 남았다. → **하나의 일관된 1차 출처·정확한 버전/특성 선택을 고정**하고, 2차 출처는 근거 재확인/오류 발견에만 사용한다.
- **설명 과다 실패:** 독자가 다음 GCD를 선택하는 조건 대신 `상황에 따라`, `특성에 따라 다름` 같은 회피 문장을 반복하여 실전 정보 밀도를 낮췄다. → 사실이라면 **어떤 특성? 어떤 수치? 어떤 행동 변화?**를 같은 위치에 적는다. 확인되지 않으면 섹션을 검토 대기로 남긴다.
- **QA 대리 지표 실패:** 표/장 수, 기술 링크 수, 브라우저 JS PASS, 기존 전문화의 byte parity가 **신규 콘텐츠의 판단 정확성**을 입증하지 못한다. → 구조 기능 QA와 독립적인 **게임플레이 조건 QA**를 추가.
- **국소 패치 실패:** 사용자 피드백이 교본 전체 작성 방법의 문제인데 첫 장 `overview`만 바꾸는 수정을 했다. → 한 곳의 문제 발견 시 동일한 오개념/모호함이 다른 표/오프너/고급 팁에도 있는지 **전체 범위 재감사**한다.
- **컨텍스트 오염 실패:** 이전 실패 초안과 AI 엔진 스키마·서식 관성을 내용의 근거처럼 사용했다. → 이전 초안은 <b>검토/반례 자료</b>로만 취급하고, **새 출처의 의사결정 규칙을 독립 추출**한다.

## 2. 새 작업의 7단계 게이트

**규모 비례 적용:** 아래 게이트는 제작자가 놓치지 말아야 할 **검증 관점**이며, 단일 규칙 확인까지 모두 한 장짜리 범위 표·완전한 테스트 보고서를 의무화하는 절차가 아니다. 신규 전문화/전체 재작성은 전체 범위에, 작은 UPDATE는 영향을 받는 조건·다른 장의 연결·실제 HTML 변경에만 비례 적용한다. Wowhead 내부 문맥으로 해결되지 않는 쟁점은 보조 공략의 **그 부분만** 검증한다. 계속 모호하면 보류한다. 새로운 검사기나 단계는 같은 실패 원인의 반복·실제 품질 기여가 입증된 경우에만 고려한다.

**과거 사례 대조:** 원본 V11의 정상적인 구조 다양성은 보존한다(사례집 P01~P03). 생존 V1/V2의 반복 조건 손실은 추출 단계까지 확대 감사한다(N02/N04). 비전의 출처 연결만으로 게임플레이 승인하지 않는다(N05). 파괴 흑마법사의 단발성 경계 불명확성은 기존 보조 출처 정책으로 처리하며 별도 검증 엔진을 만들지 않는다(사례집 §13).

### Gate A — 자료와 범위 확정

1. 전문화·패치·기간·콘텐츠 타입(ST/AoE)·영웅 특성·선택 특성·세트 효과 중 **이번 작업의 판단을 바꾸는 범위**를 명확히 한다. 신규 전문화 전체 제작 시에는 한 장짜리 범위 표가 유용하지만, 단일 규칙 확인에서는 짧은 문맥 기록으로 충분하다.
2. 사용자가 지정한 출처가 있으면 우선하고, 없으면 **Wowhead 하나를 기본 공략**으로 정해 게시/수정일과 패치가 맞는지 확인한다. 추가 공략은 필요한 판단 쟁점의 보조 검증으로만 사용하고 기준 공략의 우선순위/오프너와 섞지 않는다.
3. 공식 변경 노트/검증된 특성 데이터에서 **해당 패치에서 제거된 기술·변경된 특성**을 확인한다. 없는 주문을 포함하는 오래된 공략은 보조 자료에서도 가려낸다.
4. 출처가 없거나 동적 로딩으로 표 일부를 읽지 못하면 접근 가능한 다른 **같은 패치 자료**로 보완하고 무엇을 어디서 확인했는지 기록한다.

### Gate B — 문장보다 먼저 '게임 상태 → 조건 → 행동' 추출

모든 주요 우선순위 행을 아래 논리 단위로 분석한다.

- **조건 식별자:** 영웅 특성, 단일/광역, 관련 선택 특성, 대상 수, 버프/디버프, 중첩, 충전, 쿨다운·시간, 위치, 자원.
- **판정식:** `buff_active`, `stacks >= n`, `seconds_until_full_charge <= n`, `focus >= n`, `hero == ...`처럼 추론 가능한 상태 조건.
- **행동:** 지금 사용할 기술(이전에 쓰는지/후에 쓰는지까지).
- **이유:** 버프 소모, 추가 발동, 낭비 방지, 피해 창 정렬 같은 구체적 인과관계.
- **예외:** 선택 특성 ON/OFF, 쫄 출현, 적 이동, 상충하는 발동 규칙.
- **근거:** URL과 실제 확인된 원문 섹션 또는 주문 데이터. 다른 규칙을 근거로 추정하지 않는다.

행동만 있고 조건을 말할 수 없으면 **최종 우선순위 목록에 넣지 않는다.** 확인 가능한 고정 쿨 사용은 `사용 가능할 때`라고 명확히 쓸 수 있지만, 실제로 임계 조건이 있는 기술에 그렇게 써서는 안 된다.

### Gate C — 모순·반례 검증

각 고가치 메커니즘에서 **실제 행동이 갈리는 상태 분기와 경계**를 비교한다. 최소 개수 자체를 품질 통과 조건으로 쓰지 않는다.

- **능력 선택 OFF vs ON:** 예: 쌍둥이 송곳니 미선택이면 제압 직전 창끝 2 이상, 선택이면 0에서 시작해 3생성·1소모. 조건을 합쳐 `중첩을 준비`로 뭉개지 않는다.
- **임계 바로 아래 vs 위:** 0/1/2/3중첩, 폭탄 충전 완충, 집중 50 미만/이상.
- **재사용 시점:** 오프너와 지속 딜 우선순위에 같은 쿨기의 모순이 없는지 확인.
- **연계 충돌:** 무리의 지도자 쌍둥이 송곳니 사용 시 제압 후 창끝 2중첩이 남지만 첫 살상 명령으로 쇄도를 발동해야 함 → 창끝 과충전 위험과 쇄도 가치의 상충을 숨기지 않음.
- **특성 오독:** 서로 다른 영웅 특성의 조건을 하나의 표에 섞지 않는다.
- **패치 오독:** 제거/교체된 기술이 사용 행동으로 남지 않아야 한다.

`다름`/`상황에 따라`/`가능하면`을 쓰면 **직접 변하는 상태와 참일 때 행동을 특정하는 문장이 뒤따르는가** 반드시 검사한다. 답이 없으면 해당 문장을 고치거나 보류한다.

### Gate D — 정보 구조는 결정 문제에 맞춰 고른다

**정답은 고정 8장/5행/34행이 아니다.** 각 전문화에서 중요한 판단 분기에 맞춰 표·흐름·팁·도식 구조를 조절한다.

- **첫 화면:** 단일/광역 지속 딜, 단일/광역 오프너, 핵심 변수를 요약한다. 영웅 특성별 차이가 크면 별도 전환 표. 기존 V11의 다섯 항목은 좋은 출발점이지 무조건 5행 제한은 아니다.
- **본 우선순위:** 기본 열은 `순위 / 행동 / 사용 조건`. 조건은 변수 정의 후 `M = 10`, `M ≥ 5`, `남은 쿨 ≤ n × M초`와 같은 짧은 수치·비교식 또는 정확한 ON/OFF 분기로 표현한다. 수식은 의미가 명확할 때만 사용한다. 이유·상호작용은 실제 판단에 필요한 경우 해당 행의 `?` 팁으로 연결한다.
- **원리:** `수치 → 발동 → 후속 행동 → 실패 예시` 순서. 같은 일반 원칙을 여러 장에서 장황하게 반복하지 않는다.
- **예외:** 단일/광역, 영웅 특성, 선택 특성별로 해당 규칙 바로 옆에 명시. 전혀 다른 상황의 예외를 모아서 추상적으로 적지 않는다.
- **고급 운용:** 실제로 결정이 바뀌는 1~2개 사례를 선택해 입력 상태/선택 행동/왜 다른 기술이 아닌지 명시.
- **기술 설명/글로서리:** 정말 새 정보를 더하는 내용만 보유. 아이콘 자체의 수를 높이는 것이 목표가 아니다.
- 기존 V11 7개에서 각기 **화염 발화·마무리, 냉기 중첩, 냉죽 자원, 사격 버프, 야수 충전, 잠행 CP/춤, 암살 출혈·독**이라는 적합한 모델을 참고한다. 형식을 복제하기보다 **조건 명시 방식**을 재사용한다.

### Gate E — 정보밀도/출처 품질 감사

- 실제 명칭/수치가 있는 원문의 조건을 `적절할 때`/ `빌드에 따라` 같은 문장으로 바꾸지 않는다.
- **숫자/상태/특성명/시간/대상 수**가 한 번이라도 의미를 바꾸는 기술은 그 트리거를 본 표나 문맥에 표시한다.
- 한 문장이 단지 `확인하세요`, `주의하세요`, `상황에 맞게 사용하세요`만 말하면 제거하거나 실제 행동/원인으로 대체한다. **판단 정보가 없는 개념적 설명·중복 설명은 삭제**한다. 조건·수치·A/B 결과·예외를 남긴 뒤 필요한 배경만 설명한다. 조건이 불명확하면 원문·주문 데이터를 확인하고 미확인 수치를 만들어 채우지 않는다.
- 출처가 서로 다르면 (1) 패치 (2) 추천 빌드 (3) 특성 선택 (4) 대상 수가 같은지 먼저 확인하고, 그래도 충돌하면 한 개의 일반화된 정답을 만들지 않는다.
- **저작권:** 원문을 한국어로 길게 번역해 복제하지 않고 검증한 메커니즘을 독자적인 조건/행동 설명으로 집필한다.

### Gate F — 실물 HTML/UX와 의미 QA 분리

**콘텐츠 QA:** 기준 자료와 공식 사실 근거에서 기대 행동을 교본과 독립적으로 도출하고, 실제 주요 결정/오프너·영웅 특성·임계값·상위 우선권·상태 전이·교차 설명을 대조한다. **고정 6개 반례 할당량은 폐지**하며 검증한 분기와 미검증 분기를 명시한다. 불완전한 근거만으로 자동 PASS/FAIL하지 않는다.

**코드 QA:** 원본 비대상 전문화의 **raw HTML 바이트 동일**, UI·영웅 전환·`?`/`!`·툴팁·브라우저 오류·모바일 넘침·목차 링크 검사. 기존 V11의 대응 교본(예: 냉기 주문술사)과 소제목·본문·표의 실제 계산 CSS(크기·굵기·줄 높이·여백·색상)를 비교하고, 링크 글자의 baseline·font-size·line-height와 주문 ID 기반 아이콘 매핑을 점검한다. 표 길이는 실제 정보량에 맞추되 공통 레이아웃을 재사용한다. 외부 이미지가 차단되면 매핑 검증과 실제 로딩 확인을 구분한다.

**의미 검증 주장 범위:** 문서/공식 주문/패치 노트 기반 내용 확인 ≠ 개인 계정 시뮬레이션·실전 로그로 최적화 증명. 실제 하지 않은 검증은 PASS라 보고하지 않는다.

### Gate G — 사용자 피드백을 재발 방지 지식으로 전환

반복 요청에서 품질을 높이려면 **기존 결과를 무조건 덧붙여 재사용하지 않는다**. 모든 발견에서 범용성은 평가하되, 일회성·기존 출처 정책으로 해결되는 사안을 반드시 새로운 범용 개발로 전환하지 않는다. 사용자 피드백을 (a) 공통 원칙 결함 (b) 전문화별 사실 결함 (c) UI 결함으로 분류한다. 공통 결함이면 **기존 정상 사례에서 오탐이 없는지, 새 전문화에도 적용되는지 검증한 뒤** 다음 제작 검사에 반영한다. 사실 결함이면 패치/빌드 근거를 보정, UI 결함이면 재사용 컴포넌트에 미치는 영향을 검토한다.

완성본은 사용자 승인 전 **검토본**. 다음 정본 승격 시 승인된 HTML의 파일/해시를 비공개로 등록한 뒤 비교 기준을 새 버전으로 옮긴다. GitHub PUBLIC에 원본 교본을 올려 자동화 성공을 연출하지 않는다.

## 3. 이 문서 자체의 지속 개선

작업별로 **실제로 확인한 근거와 한계만** 기록한다. 최소 범위는 (1) 기준 패치·자료·적용 빌드, (2) 수정/새로 집필한 핵심 상태→행동 규칙과 미검증 사항, (3) 수행한 콘텐츠/HTML 검증과 실제 사용자 의견이다. 작은 수정은 변경된 부분만 기록한다. 글자 수·행 수·시험 개수·정해진 양식 자체는 완료 기준이 아니다.

**우선 원칙:** 결과물이 더 나빠졌다면 '스키마 완성도'로 합리화하지 않는다. 원본 조건→행동의 손실이 발생한 정확한 단계를 찾아, 다음 번에도 같은 손실이 나지 않도록 *의미 자체의 검증 게이트*를 추가한다.

## 4. 범용화 사례집과 오탐 방어

과거 실데이터 V11·비전·생존의 정상/실패 사례에 대한 **후향적 대조 결과**는 [QUALITY_GENERALIZATION_CASEBOOK](QUALITY_GENERALIZATION_CASEBOOK.md)에 둔다. 새 품질 규칙을 도입할 때는 실제 결함 탐지뿐 아니라 기존 정상 전문화를 잘못 실패 처리하는 **오탐**과 적용되지 않는 특수 사례를 검사한다. 비교표/흐름도 수, CSS 클래스, 기술명 문자열, 출처 사이트 수를 단독 품질 승인 근거로 쓰지 않는다. 이 사례집의 범용 원칙은 독립 전문화에서 반복 품질 개선을 실증하기 전까지 자동 강제 규칙이 아니다.

## 5. 최종 품질 판정과 자기 검증

제작 Gate A~G의 절차 준수와 **완성 교본의 실제 품질은 별도**다. [QUALITY_FIRST_POLICY](QUALITY_FIRST_POLICY.md)의 Q0 사실 정확성, Q1 판단 정확성/완결성, Q2 이해·응용, Q3 실전 사용성, Q4 변경 안정성으로 판정한다. Q0/Q1/Q4 실패를 콘텐츠 분량·시각적 완성도로 상쇄하지 않는다. `통과/실패/부분 확인/미검증`을 증거 범위와 함께 표시한다.

**품질 기준도 평가 대상이다.** 과거 실패 사례를 탐지하지만 기존 V11의 올바른 표/설명을 잘못 탈락시키지 않는지 양성·음성 대조를 확인한다. 품질 규격 개정 전후 실제 개선·오탐·회귀를 비교하고, 독립 전문화 반복 검증 전에는 일반화 효과를 확정하지 않는다. 작업의 첫 질문은 '구현 가능한가'가 아니라 **'어떤 독자 판단·제작 결과가 왜 좋아지는가'**다.
