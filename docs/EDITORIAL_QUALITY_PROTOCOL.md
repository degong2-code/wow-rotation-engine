# EDITORIAL QUALITY PROTOCOL — 결정 가능성 우선 교본 집필 규격 (2026-11-11)

> **우선순위: 자료 충실도 → 시전 판단 가능성 → 예외·원인 설명 → 사용자 경험 → HTML 무결성.**
> 이 문서는 ChatGPT가 반복 제작할 때 실제 교본 품질이 높아지도록 하는 콘텐츠 제작 절차다. 고정 장 수/문장 수/템플릿의 통과를 제품 성공으로 오인하지 않는다.

## 1. 실패 원인과 수정 방향

- **Template-first 실패:** 이전 생존 초안은 먼저 `priority(action, reason)`의 2열 데이터로 원문을 분배했다. 실전의 3원소 **순위/행동/조건**이 분리되지 않으므로 수치·발동 조건이 글 속으로 묻혔다. → **규칙부터 적고 그 규칙을 표현할 UI를 나중에 선택한다.**
- **출처 혼합 실패:** 한 패치/하나의 실제 특성 분기를 고정하지 않고 Wowhead·Icy Veins·Method의 시점을 섞었다. 예를 들어 옛 `Flamefang Pitch`가 목록에 남았다. → **하나의 일관된 1차 출처·정확한 버전/특성 선택을 고정**하고, 2차 출처는 근거 재확인/오류 발견에만 사용한다.
- **설명 과다 실패:** 독자가 다음 GCD를 선택하는 조건 대신 `상황에 따라`, `특성에 따라 다름` 같은 회피 문장을 반복하여 실전 정보 밀도를 낮췄다. → 사실이라면 **어떤 특성? 어떤 수치? 어떤 행동 변화?**를 같은 위치에 적는다. 확인되지 않으면 섹션을 검토 대기로 남긴다.
- **QA 대리 지표 실패:** 표/장 수, 기술 링크 수, 브라우저 JS PASS, 기존 전문화의 byte parity가 **신규 콘텐츠의 판단 정확성**을 입증하지 못한다. → 구조 기능 QA와 독립적인 **게임플레이 조건 QA**를 추가.
- **국소 패치 실패:** 사용자 피드백이 교본 전체 작성 방법의 문제인데 첫 장 `overview`만 바꾸는 수정을 했다. → 한 곳의 문제 발견 시 동일한 오개념/모호함이 다른 표/오프너/고급 팁에도 있는지 **전체 범위 재감사**한다.
- **컨텍스트 오염 실패:** 이전 실패 초안과 AI 엔진 스키마·서식 관성을 내용의 근거처럼 사용했다. → 이전 초안은 <b>검토/반례 자료</b>로만 취급하고, **새 출처의 의사결정 규칙을 독립 추출**한다.

## 2. 새 작업의 7단계 게이트

### Gate A — 자료와 범위 확정

1. 전문화·패치·기간·콘텐츠 타입(ST/AoE)·영웅 특성·선택 특성·세트 효과 범위를 **한 장짜리 범위 표**로 정한다.
2. 신뢰할 수 있는 실제 **기준 공략 1개**를 정해 게시/수정일과 패치가 맞는지 확인한다. 복수 출처를 쓰더라도 기준 공략의 우선순위와 오프너를 분해해서 뒤섞지 않는다.
3. 변경 노트/특성 데이터에서 **해당 패치에서 제거된 기술·변경된 특성**을 확인한다. 없는 주문을 포함하는 오래된 공략은 보조 자료에서도 가려낸다.
4. 출처가 없거나 동적 로딩으로 표 일부를 읽지 못하면 접근 가능한 다른 **같은 패치 자료**로 보완하고 무엇을 어디서 확인했는지 기록한다.

### Gate B — 문장보다 먼저 '게임 상태 → 조건 → 행동' 추출

모든 주요 우선순위 행을 아래 논리 단위로 분석한다.

- **조건 식별자:** 영웅 특성, 단일/광역, 관련 선택 특성, 대상 수, 버프/디버프, 중첩, 충전, 쿨다운·시간, 위치, 자원.
- **판정식:** `buff_active`, `stacks >= n`, `seconds_until_full_charge <= n`, `focus >= n`, `hero == ...`처럼 추론 가능한 상태 조건.
- **행동:** 지금 사용할 기술(이전에 쓰는지/후에 쓰는지까지).
- **이유:** 버프 소모, 추가 발동, 낭비 방지, 피해 창 정렬 같은 구체적 인과관계.
- **예외:** 선택 특성 ON/OFF, 쫄 출현, 적 이동, 상충하는 발동 규칙.
- **근거:** URL과 실제 확인된 원문 섹션 또는 주문 데이터. 다른 규칙을 근거로 추정하지 않는다.

행동만 있고 조건을 말할 수 없으면 **최종 우선순위 목록에 넣지 않는다.** 확인 가능한 고정 쿨 사용은 `사용 가능할 때`라고 명확히 쓸 수 있지만, 실제로 임계 조건이 있는 기술에 그렇게 써서는 안 된다.

### Gate C — 모순·반례 검증

각 고가치 메커니즘에 최소 두 경우를 비교한다.

- **능력 선택 OFF vs ON:** 예: 쌍둥이 송곳니 미선택이면 제압 직전 창끝 2 이상, 선택이면 0에서 시작해 3생성·1소모. 조건을 합쳐 `중첩을 준비`로 뭉개지 않는다.
- **임계 바로 아래 vs 위:** 0/1/2/3중첩, 폭탄 충전 완충, 집중 50 미만/이상.
- **재사용 시점:** 오프너와 지속 딜 우선순위에 같은 쿨기의 모순이 없는지 확인.
- **연계 충돌:** 무리의 지도자 쌍둥이 송곳니 사용 시 제압 후 창끝 2중첩이 남지만 첫 살상 명령으로 쇄도를 발동해야 함 → 창끝 과충전 위험과 쇄도 가치의 상충을 숨기지 않음.
- **특성 오독:** 서로 다른 영웅 특성의 조건을 하나의 표에 섞지 않는다.
- **패치 오독:** 제거/교체된 기술이 사용 행동으로 남지 않아야 한다.

`다름`/`상황에 따라`/`가능하면`을 쓰면 **직접 변하는 상태와 참일 때 행동을 특정하는 문장이 뒤따르는가** 반드시 검사한다. 답이 없으면 해당 문장을 고치거나 보류한다.

### Gate D — 정보 구조는 결정 문제에 맞춰 고른다

**정답은 고정 8장/5행/34행이 아니다.** 각 전문화에서 중요한 판단 분기에 맞춰 표·흐름·팁·도식 구조를 조절한다.

- **첫 화면:** 단일/광역 지속 딜, 단일/광역 오프너, 핵심 변수를 요약한다. 영웅 특성별 차이가 크면 별도 전환 표. 기존 V11의 다섯 항목은 좋은 출발점이지 무조건 5행 제한은 아니다.
- **본 우선순위:** 기본 열은 `순위 / 행동 / 사용 조건`. 이유·상호작용은 해당 행의 `?` 팁으로 연결해 표 자체를 복잡하게 만들지 않는다.
- **원리:** `수치 → 발동 → 후속 행동 → 실패 예시` 순서. 같은 일반 원칙을 여러 장에서 장황하게 반복하지 않는다.
- **예외:** 단일/광역, 영웅 특성, 선택 특성별로 해당 규칙 바로 옆에 명시. 전혀 다른 상황의 예외를 모아서 추상적으로 적지 않는다.
- **고급 운용:** 실제로 결정이 바뀌는 1~2개 사례를 선택해 입력 상태/선택 행동/왜 다른 기술이 아닌지 명시.
- **기술 설명/글로서리:** 정말 새 정보를 더하는 내용만 보유. 아이콘 자체의 수를 높이는 것이 목표가 아니다.
- 기존 V11 7개에서 각기 **화염 발화·마무리, 냉기 중첩, 냉죽 자원, 사격 버프, 야수 충전, 잠행 CP/춤, 암살 출혈·독**이라는 적합한 모델을 참고한다. 형식을 복제하기보다 **조건 명시 방식**을 재사용한다.

### Gate E — 정보밀도/출처 품질 감사

- 실제 명칭/수치가 있는 원문의 조건을 `적절할 때`/ `빌드에 따라` 같은 문장으로 바꾸지 않는다.
- **숫자/상태/특성명/시간/대상 수**가 한 번이라도 의미를 바꾸는 기술은 그 트리거를 본 표나 문맥에 표시한다.
- 한 문장이 단지 `확인하세요`, `주의하세요`, `상황에 맞게 사용하세요`만 말하면 제거하거나 실제 행동/원인으로 대체한다.
- 출처가 서로 다르면 (1) 패치 (2) 추천 빌드 (3) 특성 선택 (4) 대상 수가 같은지 먼저 확인하고, 그래도 충돌하면 한 개의 일반화된 정답을 만들지 않는다.
- **저작권:** 원문을 한국어로 길게 번역해 복제하지 않고 검증한 메커니즘을 독자적인 조건/행동 설명으로 집필한다.

### Gate F — 실물 HTML/UX와 의미 QA 분리

**콘텐츠 QA:** 주 기준 자료의 각 중요 결정/오프너와 재집필 결과 대조. 모순·누락·근거 없는 창작이 없는지 감사. 최소 6개의 `상태 → 다음 행동` 반례 문제를 실제 가이드 문구로 풀 수 있어야 한다.

**코드 QA:** 원본 비대상 전문화의 **raw HTML 바이트 동일**, UI·영웅 전환·`?`/`!`·툴팁·브라우저 오류·모바일 넘침·목차 링크 검사.

**의미 검증 주장 범위:** 문서/공식 주문/패치 노트 기반 내용 확인 ≠ 개인 계정 시뮬레이션·실전 로그로 최적화 증명. 실제 하지 않은 검증은 PASS라 보고하지 않는다.

### Gate G — 사용자 피드백을 재발 방지 지식으로 전환

반복 요청에서 품질을 높이려면 **기존 결과를 무조건 덧붙여 재사용하지 않는다**. 사용자 피드백을 (a) 공통 원칙 결함 (b) 전문화별 사실 결함 (c) UI 결함으로 분류한다. 공통 결함이면 **모든 다음 제작에서 검사를 추가**, 사실 결함이면 패치/빌드 근거를 보정, UI 결함이면 재사용 컴포넌트만 변경한다.

완성본은 사용자 승인 전 **검토본**. 다음 정본 승격 시 승인된 HTML의 파일/해시를 비공개로 등록한 뒤 비교 기준을 새 버전으로 옮긴다. GitHub PUBLIC에 원본 교본을 올려 자동화 성공을 연출하지 않는다.

## 3. 이 문서 자체의 지속 개선

이 프로토콜을 적용한 각 전문화에서 다음을 기록하되, 글자 수/행 수만을 통과 기준으로 삼지 않는다.

| 기록 | 완료 기준 |
|---|---|
| 기준 공략과 패치 | 실제 날짜·빌드가 확인됨 |
| 사용된 규칙 | 상태·수치·특성·행동·근거가 연결됨 |
| 상충 특성/버전 | 무엇이 변하는지와 후속 행동 명시 |
| 우선순위 | 3열의 유효한 실행 조건 |
| 반례 테스트 | 영웅/특성 ON-OFF·충전/중첩 경계 통과 |
| 화면 검증 | raw 본문 보존·버튼/툴팁·모바일/데스크톱 |
| 최종 문장 감사 | 의미 없는 회피 표현·중복 일반론 제거 |
| 사용자 평가 | 향후 수정에 반영된 평가 항목과 시점 |

**우선 원칙:** 결과물이 더 나빠졌다면 '스키마 완성도'로 합리화하지 않는다. 원본 조건→행동의 손실이 발생한 정확한 단계를 찾아, 다음 번에도 같은 손실이 나지 않도록 *의미 자체의 검증 게이트*를 추가한다.
